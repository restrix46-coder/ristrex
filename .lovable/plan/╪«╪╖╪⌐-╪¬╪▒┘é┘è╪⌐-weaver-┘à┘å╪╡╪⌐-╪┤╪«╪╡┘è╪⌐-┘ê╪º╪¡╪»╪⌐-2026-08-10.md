# خطة ترقية Weaver — منصة شخصية واحدة

الهدف: منصة شخصية موثوقة يمكن الاعتماد عليها لبناء مشاريع حقيقية للزبائن من الألف إلى الياء، مع جودة احترافية وتجربة استخدام واضحة.

## المرحلة 1: جعل الوكيل ينجز مشروعاً حقيقياً بنسبة 100%

### 1.1 تتبع حالة البناء بدقة
- إضافة `build_state` و `next_action` واضحة لكل مشروع في قاعدة البيانات.
- كل عملية تنفيذ يجب أن تقرأ الحالة الفعلية من الملفات والمهام والتقارير، لا تبدأ من الصفر.
- إنشاء `build-reconciliation` service: مقارنة بين المهام المخططة والملفات الموجودة، وتحديد الفجوات.

### 1.2 حلقة التنفيذ الذاتي-التصحيحي
- تفعيل `auto_repair` وتقليص عدد المحاولات الفاشلة قبل التصعيد.
- عند فشل مهمة، الوكيل يجب أن يحدد: السبب، الملف المعني، التصحيح المقترح، ثم يعيد التنفيذ.
- تخزين سجل التصحيحات (`repair_log`) لكل مشروع لتحليل الأنماط.

### 1.3 فحص شامل قبل الادعاء بالنجاح
- إطلاق `run_checks` تلقائياً بعد كل ملف مكتوب.
- عدم الانتقال إلى مرحلة النشر إلا إذا مرّ الفحص بنجاح (`ok: true`).
- إضافة فحص متصفحي (Playwright) يلتقط أخطاء console وروابط معطلة ويتحقق من responsive.

### 1.4 نشر موثوق
- تحسين `deployPlatform` و `publish_site` ليعملا بشكل متزامن مع الإشعارات الواضحة.
- إضافة `verifyDeployHealth` يتحقق من أن الموقع الناتج يستجيب بـ 200 ويحمل محتوى حقيقي.
- فصل قواعد بيانات المشاريع المبنية عن قاعدة البيانات الرئيسية للمنصة (VPS/DB مستقل لكل مشروع).

## المرحلة 2: رفع جودة التصميم الناتج

### 2.1 قوالب احترافية جاهزة
- توسيع `design-library.ts` بقوالب متخصصة: SaaS، متجر، portfolio، dashboard، landing page.
- كل قالب يتضمن: CSS كامل، هيكل HTML، وتعليمات استخدام.
- تفعيل قالب افتراضي احترافي عند بدء أي مشروع بدلاً من الصفحة البيضاء.

### 2.2 ناقد بصري أكثر صرامة
- تحسين `design-critic.server.ts` ليتحقق من: typography، spacing، color palette، visual hierarchy، mobile responsiveness.
- تمرير نتيجة النقد إلى الوكيل كـ feedback loop قبل النشر.
- منع النشر إذا لم يحصل التصميم على `VERDICT: pass`.

### 2.3 مكتبة أصول متكاملة
- تكامل `brand-kit.ts` مع جميع المواقع المُولدة.
- توفير أيقونات، خطوط، وألوان متناسقة مع RTL.
- توليد صور احترافية تلقائياً للأقسام الرئيسية.

## المرحلة 3: تحسين تجربة الاستخدام الشخصية

### 3.1 واجهة أبسط وأسرع
- إعادة تصميم `app-shell.tsx` لتقليل الفوضى: إخفاء الأقسام النادرة في قائمة إعدادات، وإبراز المحادثة والمعاينة والمهام.
- تحسين الأداء عبر code splitting للمسارات الثقيلة (monitor, settings, runtime-panel).
- إضافة اختصارات لوحة مفاتيح للمهام الشائعة.

### 3.2 شفافية كاملة أثناء البناء
- شريط تقدم واضح يُظهر: المرحلة الحالية، المهمة النشطة، المدة، والتكلفة المتراكمة.
- سجل أخطاء قابل للنسخ والتوسيع.
- زر "إيقاف/استئناف" للتحكم في الوكيل.

### 3.3 حالات فارغة و onboarding
- أول دخول إلى `/app` يعرض قالباً جاهزاً للبدء.
- إضافة تلميحات تفاعلية توضح كيفية كتابة طلب جيد.
- نماذج طلبات محفوظة (prompts) لأنواع المشاريع الشائعة.

## المرحلة 4: استقرار النشر والاستضافة

### 4.1 فصل المشاريع عن المنصة
- كل مشروع يُنشر على VPS منفصل أو container منعزل.
- قاعدة بيانات مستقلة لكل مشروع، مع إمكانية تصدير SQL كامل.
- عدم مشاركة أسرار المنصة مع مشاريع الزبائن.

### 4.2 تسريع التكرار
- نظام `git-sync` موثوق يدفع الملفات إلى repo الخاص بالمشروع.
- build cache مشترك لأدوات البناء (npm, docker layers).
- hot-reload للمعاينة المحلية قبل النشر.

### 4.3 مراقبة وصيانة
- `monitor` panel يُظهر: صحة المشاريع المنشورة، آخر خطأ، حالة الخادم، وإشعارات WhatsApp/Telegram.
- إعادة التشغيل التلقائي للخدمات المتوقفة.
- نسخ احتياطي أسبوعي لقواعد البيانات والملفات.

## الترتيب المقترح للتنفيذ

1. **تتبع حالة البناء بدقة** (الأساس)
2. **حلقة التصحيح الذاتي** (يحل معظم مشاكل عدم الإنجاز)
3. **قوالب تصميم احترافية** (يرفع جودة المخرجات فوراً)
4. **شفافية البناء وإعادة تصميم الواجهة** (يحسن تجربة الاستخدام)
5. **فصل المشاريع والاستضافة المستقلة** (يضمن الأمان والقابلية للتوسع)
6. **المراقبة والنسخ الاحتياطي** (يضمن الاستقرار طويل المدى)

## النتيجة المتوقعة

بعد تنفيذ هذه الخطة، يصبح Weaver قادراً على:
- بناء مشروع متوسط التعقيد من الطلب إلى الرابط العام بدون تدخل يدوي.
- إنتاج مواقع بصرية احترافية ومتجاوبة.
- إعلام المستخدم بوضوح بما يحدث في كل لحظة.
- نشر المشاريع بشكل آمن على بنية تحتية منفصلة.
